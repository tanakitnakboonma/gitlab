# Reflection — Lab 02 BJT DC Bias Web App

## 1. อะไรที่ AI ช่วย และอะไรที่ตรวจเอง

AI ช่วยตั้งโครงโปรเจกต์ Flask แบบ multi-file, เขียนโครง unittest,
สร้าง template/CSS ตาม mockup และช่วยร่างเอกสาร ผมตรวจส่วนวิศวกรรมเองโดย

- คำนวณมือด้วยสมการ voltage-divider bias แล้วเทียบค่ากับโปรแกรม
  (VB = 1.9422 V, VE = 1.2422 V, VC = 9.2943 V, VCE = 8.0521 V,
  IC = 1.2299 mA) ค่าจากโปรแกรมตรงกับมือภายใน tolerance ที่กำหนด
- ตรวจว่าหน่วยสอดคล้องกัน: อินพุต R เป็น kΩ แล้วแปลงเป็น Ω ก่อนคำนวณ,
  กระแสแสดงเป็น mA/µA และแรงดันเป็น V
- ลองกรอกค่าผิดจริงใน Browser (ค่าว่าง, `0`, ตัวอักษร, ค่าที่ทำให้เกิด
  Cutoff และ Saturation) เพื่อดูว่า error/warning แสดงถูกและหน้าไม่ล้ม
- review โค้ดอีกรอบด้วย fresh context แล้วพบว่า error ของ R1/R2/RC/RE
  บอกชื่อ field ไม่ชัด ผมจึงเพิ่ม `label` ให้ `kohm_to_ohm` และเพิ่มเทสต์
  ยืนยันว่าข้อความมีชื่อ field จริง

สิ่งที่ต้องระวังคือ AI อาจสร้างเทสต์ที่ "ผ่านง่ายเกินไป" เช่น เดิมเทสต์
Cutoff เช็คแค่ว่ามีคำว่า `Cutoff` ซึ่งอยู่ในบรรทัดสถานะอยู่แล้ว
จึงต้องเพิ่มการตรวจ `class="warning"` และข้อความเฉพาะของ warning

## 2. การแยก Frontend / Backend / Logic มีผลต่อการแก้สมการอย่างไร

โปรเจกต์แยกเป็นสามชั้น:

- `dc_bias.py` เก็บสมการและ validation ล้วน ๆ ไม่รู้จัก Flask หรือ HTML
- `app.py` รับ HTTP, แปลง kΩ → Ω และเรียก `calculate_dc_bias`
- `templates/index.html` + `static/style.css` แสดงผลเท่านั้น

ผลคือถ้าแก้สมการ เช่น เปลี่ยนวิธีคิด IB หรือเพิ่มการเตือน ผมแก้ที่
`dc_bias.py` ที่เดียวแล้วรัน `tests/test_dc_bias.py` ได้ทันที โดยไม่ต้อง
แตะ HTML เลย ในทางกลับกันถ้าเปลี่ยนหน้าตาเว็บ เช่น ย้ายช่อง VBE
หรือเปลี่ยนสี status box ผมแก้แค่ template/CSS และเทสต์ HTTP
(`tests/test_web.py`) ยังใช้ตรวจว่า field และผลลัพธ์ยังครบเหมือนเดิม

การแยกแบบนี้ทำให้ข้อผิดพลาดถูกจำกัดวง: bug เรื่องหน่วยจะอยู่ที่ `app.py`
bug เรื่องสมการจะอยู่ที่ `dc_bias.py` และ bug เรื่องการแสดงผลจะอยู่ที่
template/CSS ทำให้หาต้นเหตุได้เร็วขึ้น

## 3. ข้อจำกัดของ Forward-Active Approximation

สมการที่ใช้ถือว่าทรานซิสเตอร์อยู่ใน Forward-Active คือรอยต่อ Base–Emitter
ไบแอสตรง และ Collector–Base ไบแอสกลับ รวมถึงถือว่า β และ VBE คงที่
ไม่คิด Early effect, อุณหภูมิ หรือความต้านทานภายใน จึงใช้ได้ดีเมื่อวงจร
อยู่ในย่านทำงานปกติ

ถ้า `VTH ≤ VBE` หรือ `IB ≤ 0` ทรานซิสเตอร์จะอยู่ใน Cutoff สมการ
Forward-Active ไม่ใช่คำตอบจริง เพราะกระแสควรเป็นศูนย์ ไม่ใช่ค่าลบ
หรือค่าน้อยมากที่สมการให้มา ในทำนองเดียวกันถ้า `VCE < 0.2 V` ทรานซิสเตอร์
อิ่มตัว (Saturation) และกระแส Collector ไม่ได้เป็น β เท่าของ IB อีกต่อไป
ดังนั้นค่าที่โปรแกรมแสดงในสองกรณีนี้จึงเป็นเพียง "ค่าประมาณจากสมการ"
ไม่ใช่จุดทำงานจริง ผมจึงให้โปรแกรมคำนวณแล้วติด warning แทนการซ่อนค่า
เพื่อให้เห็นชัดว่าสมมติฐานใช้ไม่ได้เมื่อไร

เมื่อเทียบกับ ngspice โปรแกรม SPICE จะแก้สมการอุปกรณ์แบบไม่เชิงเส้น
และเลือกโหมดการทำงานของทรานซิสเตอร์เอง จึงจำลอง Cutoff/Saturation
ได้ใกล้จริงกว่า แบบจำลองนี้ตั้งใจให้เรียบง่ายเพื่อการเรียนรู้ DC Bias
ไม่ใช่แทนเครื่องจำลองวงจร

## 4. ถ้ามีเวลาอีก 1 ชั่วโมง จะทำอะไรต่อ

ถ้ามีเวลาอีกหนึ่งชั่วโมง ผมจะ

1. เพิ่มกราฟ DC Load Line (`IC` เทียบ `VCE`) เพื่อให้เห็นจุดทำงาน
   และขอบเขต Cutoff/Saturation ได้ด้วยภาพ
2. เพิ่มการทดสอบค่า borderline เช่น `VCE` ใกล้ `0.2 V` และ
   `VTH` ใกล้ `VBE` เพื่อกันการเปรียบเทียบขอบเขตผิดพลาด
3. ปรับปรุง accessibility เช่น เพิ่ม `aria-live` ให้ status box
   และตรวจ contrast ของสี warning
4. ทำเอกสารสั้น ๆ วิธีอ่านผลลัพธ์สำหรับผู้ใช้ครั้งแรก

ทั้งหมดนี้ยังอยู่ในขอบเขต DC Bias และไม่เปลี่ยนสมการหลักของ Lab 2

## 5. สิ่งที่ได้เรียนรู้

- การเขียนเทสต์ก่อนทำให้เห็นทันทีว่า validation หรือ warning ที่คิดว่า
  ทำงานอยู่ อาจไม่มีเทสต์ยืนยันจริง
- การแยกชั้นทำให้แก้สมการได้อย่างมั่นใจโดยไม่ทำให้หน้าเว็บพัง
- warning ที่ดีต้องบอกทั้ง "เงื่อนไขที่ผิด" และ "ค่าที่แสดงเชื่อถือได้แค่ไหน"
  ไม่ใช่แค่เปลี่ยนสีกล่อง
